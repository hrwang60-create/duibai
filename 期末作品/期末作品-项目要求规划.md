## 3. 云端与第三方（要求 2c）

### 3.1 云数据库表设计

要求点名了**至少两个**：用户管理、banner。本项目共 **10 张表**。

**要求点名表（必须有）**

| 表名 | 关键字段 | 说明 |
| --- | --- | --- |
| `users` | `_id`、`openid`、`nickname`、`avatar`、`role`(`user`/`admin`)、`status`、`created_at`、`last_login` | **用户管理**：登录建档、角色控制管理端入口、封禁 |
| `banners` | `_id`、`image`、`title`、`link`、`sort`、`enabled`、`start_at`、`end_at` | **Banner**：首页轮播，支持排序与定时上下架 |

**业务表（对白特有）**

| 表名 | 关键字段 | 说明 |
| --- | --- | --- |
| `tones` | `code`、`name`、`description`、`prompt_template`、`enabled` | 6 种口吻预置，管理端可改 |
| `articles` | `_id`、`user_id`、`title`、`content`、`char_count`、`created_at` | 上传的文章 |
| `paragraphs` | `_id`、`article_id`、`seq`、`text` | 段落编号，**出处回溯的基础** |
| `scripts` | `_id`、`article_id`、`tone_code`、`status`、`line_count`、`pending_confirm`、`created_at` | 对话稿 |
| `dialogue_lines` | `_id`、`script_id`、`seq`、`speaker`、`text`、`source_paragraph`、`flag`、`confirmed` | 对话条目，`flag` 标记可疑类型 |
| `audio_segments` | `_id`、`line_id`、`speaker`、`file_id`、`duration` | 音频片段，与条目一对一（支持单句重做） |
| `gen_logs` | `_id`、`user_id`、`script_id`、`stage`、`ms`、`error_code`、`created_at` | **管理端统计用**：成功率、耗时 |
| `feedbacks` | `_id`、`user_id`、`content`、`contact`、`handled`、`created_at` | 用户反馈（管理端闭环） |

> 设计要点：`paragraphs.seq` + `dialogue_lines.source_paragraph` 这一对，
> 是"点出处能看到原文"能成立的根本，是最该保住的一条数据关系。

### 3.2 ⚠️ 关键技术约束：为什么必须用云函数中转

这一条**不做会直接卡死**，必须在报告里写明：

1. **密钥不能放前端。** 大模型 API Key 和 TTS Key 如果写在小程序代码里，解包即可拿到，等于公开泄露。
2. **小程序有域名白名单。** 请求域名必须在微信后台配置且**须 HTTPS + 已备案**，直连第三方
   API 的域名往往过不了这一关。
3. **音频不能打进包。** 小程序主包限制 2MB，音频必须存云存储、按 URL 播放。

**结论：所有第三方调用走「云函数」这一层。**

```
小程序端  →  云函数（持有密钥、组装请求）  →  大模型 API / TTS API
                    ↓
              云数据库 / 云存储
```

**职责边界**：云函数是**唯一直接对接模型**的地方，前端只跟云函数说话。
好处有三个——密钥不外泄、绕开域名白名单、模型换供应商时前端零改动。

### 3.3 第三方服务选型

| 用途 | 候选 | 建议 |
| --- | --- | --- |
| 对话稿生成 | DeepSeek / 通义千问 / 智谱 | **DeepSeek**（便宜、中文强、结构化输出稳） |
| 语音合成 | 火山引擎 / 腾讯云 / Azure | **火山引擎**（双音色自然、情感指令支持好） |
| 云端后端 | **uniCloud**（阿里云或腾讯云版） | **uniCloud** —— uni-app 原生集成，云数据库/云函数/云存储一体，免运维，最适合本作业 |

> 选 uniCloud 的理由：要求里"云服务器（云数据库）"与"第三方"是**并列**的两种方案，
> uniCloud 同时满足前者的形态要求，又不必自己租服务器、配域名备案，能把时间留给功能本身。

### 3.4 云存储

- `audio/{user_id}/{script_id}/{line_id}.mp3` —— 音频片段
- `banner/{banner_id}.jpg` —— 轮播图
- `avatar/{user_id}.jpg` —— 头像

## 8. 执行顺序与风险

### 建议顺序

1. **搭 uni-app 工程骨架 + 建 10 张云数据库表 + 初始化 banner / tones 数据**
   （表结构先立住，后面所有页面才有依赖对象）
2. **打通云函数调用大模型** —— 先跑通"文章 → 对话稿"这条核心链路
   （这是整个产品的价值所在，跑不通后面全是空壳）
3. **做 C 端 6 个必做页面**（够到 2a 的硬性线）
4. **做管理端 4 页**（拿 2d 加分）
5. **接 TTS + 播放器 + 逐句高亮**（技术难点最集中，留足时间）
6. **补齐 C 端剩余 3 页**（登录/原文查看/我的/错误页）
7. **出信息架构图 PNG**（3a）
8. **写录屏脚本 → 录制**（3b）
9. **导出云数据（脱敏）→ 打包提交**（3c）

### 风险清单

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| **ColorUI 不熟悉被问倒** | 要求明写"需充分了解模板" | 提前读其 `main.css` 类名规则与设计变量，能当场讲 |
| **小程序音频播放限制** | 逐句播放/锁屏播放可能不如预期 | 用 `uni.createInnerAudioContext()` 管播放队列；**不在录屏里承诺锁屏播放** |
| **云函数超时** | 大模型生成一条对话稿可能超 20s | 拆成"提交任务 → 轮询结果"，别做同步长请求 |
| **包体积超 2MB** | 小程序无法上传 | 音频/图片一律走云存储，不进包 |
| **密钥泄露** | 安全性质问题 | 全部密钥只在云函数环境变量里，前端零密钥 |
| **页面/组件数量算不够** | 直接卡硬性要求 | 录制前**逐个数一遍**：页面要能在 `pages.json` 里点出来，组件要能指出对应文件 |
