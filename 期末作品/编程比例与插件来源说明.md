## 四、AI 能力用在什么位置（AI 能力层与业务解耦）

**全项目只有两处调用 AI**，都在云函数里：

```
generate-dialogue   207 行   文章 → 对话稿（拼 Prompt + 三项台词校验）
tts-synthesize      167 行   对话稿 → 音频（逐句合成 + 云存储上传）
```

**解耦的落点**：两者都是**纯函数式的适配器**——
`synthOne(text, speaker)` 只负责"文字 → 音频字节"，
不认识数据库、不认识业务概念。换供应商只需改这一个函数，上层页面与业务逻辑一行不动。

**这也是"可维护"的落点**：AI 供应商会变、会涨价、会下线，
但业务逻辑不该跟着变。

### 三项台词校验（自研，写在 `generate-dialogue` 里）

| 校验 | 规则 | 不通过时 |
| --- | --- | --- |
| **出处校验** | 每句台词的 `source_paragraph` 必须是 1..段数 | 归零并标 `no_source`，进「可疑处」 |
| **括号清理** | 台词里不能残留中文括号 | 清除并标 `term`，进「可疑处」 |
| **说话人校验** | 只能是 A / B | 强制纠正 |

**这三条是"对话不是凭空编的"的机制保障**，也是人工确认点存在的原因。

## 六、结论

1. **编程比例约 7 : 3**（前端 5348 行 / 后端 2238 行），与本产品"交互即价值"的定位相符。
2. **未引入任何第三方 UI 组件库** —— 14 个组件、整套设计系统、核心交互全部自研。
3. 引入的只有课程指定的 **uni-app + uniCloud** 两个框架。
4. **AI 只用在两处**，都在云函数的可替换适配器里，且密钥全部隔离在服务端。
5. 全部 40 项云端断言通过，包含**真实调用 DeepSeek 与火山 TTS**，非 mock 数据。
