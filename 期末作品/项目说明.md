# 「对白」项目说明

> **一句话**：把一篇文章的书面语，改写成两个人的口语对话，再合成双音色音频——
> 让人在通勤、睡前这类**看不了屏幕**的碎片时间里，把一篇文章"听懂"。
>
> 本文回答三件事：**这是什么**、**要做什么**、**不做什么**。详细拆分见同目录《期末作品-项目要求规划.md》。

---

## 一、这个项目是什么

### 1. 产品名与定位

| 项 | 内容 |
| --- | --- |
| 名称 | **对白**（Duibai） |
| 一句话定位 | 把文章，聊给你听 |
| 产品形态 | 微信小程序（uni-app 一套代码，可同时发小程序 / App / H5），另带一个管理后台 |
| 赛道 | 听觉内容 / 碎片时间学习 |

### 2. 给谁用，在什么场景

**目标用户：在校学生。**

典型使用时刻：

| 场景 | 手和眼被占用 | 现在的做法 | 问题 |
| --- | --- | --- | --- |
| 通勤地铁上 | 挤、单手扶杆 | 想读篇文章，屏幕看不方便 | 只能放弃 |
| 睡前 | 关灯了 | 想复习点东西 | 看屏幕刺眼、越看越精神 |
| 做家务 / 走路 | 手在忙 | 听朗读版 | 听着累，走神 |

共同点：**想获取信息，但"看"这个动作做不了**。

### 3. 解决什么问题

不是"没人念给你听"，而是**"念出来的东西听不进去"**：

1. **书面语不适合听。** 长句、定语套定语、信息密度高。
   "光合作用的光反应阶段在类囊体薄膜上进行，产物 ATP 与 NADPH 将参与后续的暗反应"
   —— 这句读出来，听的人第三秒就丢了。
2. **一个人念稿，没有对话感。** 单声道的信息流没有"你来我往"的节奏，注意力很容易跑。
3. **光听不可靠。** 听到一个数字、一个术语，没法核对是不是念错了、是不是原文真有这句。

### 4. 和现有做法有什么不同（业务创新）

**核心不是"把文章读出来"，而是"把它改成两个人在聊"。**

| | 普通朗读 / TTS 转语音 | 「对白」 |
| --- | --- | --- |
| 内容形态 | 原文照读 | 改写成双人对谈 |
| 语言 | 书面语 | 口语、短句、有反问和追问 |
| 听感 | 听讲稿 | 听聊天 |
| 核对 | 无从核对 | **每条台词可点回原文段落** |

**改写示例**（同一段知识，两种形态）：

> **原文（书面语）**
> 光合作用的光反应阶段在类囊体薄膜上进行，产物 ATP 与 NADPH 将参与后续的暗反应。

> **对白（"抬杠"口吻）**
> 甲：等下，光反应和暗反应是分开干的？
> 乙：嗯，光反应在类囊体薄膜上，先产出 ATP 和 NADPH。
> 甲：那这俩是干嘛的？
> 乙：给下一步的暗反应供货用的。

事实没变，但变成了"有人在替我问问题"——这正是走神时能把你拉回来的东西。

### 5. 用户视角的完整流程

```
上传文章  →  选口吻  →  等生成  →  确认几处可疑点  →  听音频  →  听不清就改那一句
```

其中**「确认可疑点」是刻意加的一步**：AI 拿不准的地方（术语怎么读、某句有没有原文支撑）
会先列出来让用户过一遍，**没确认完不允许合成音频**。宁可多一步，也不要让用户听到编造的内容。

## 二、要做什么

### 1. 技术选型

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 前端 | **uni-app（Vue）** | 一套代码多端；本机已装 HBuilderX 与微信开发者工具 |
| 后端 | **uniCloud**（云数据库 + 云函数 + 云存储） | 免运维、不用备案域名，把时间留给功能 |
| 第三方 | **大模型 API**（生成对话稿）+ **TTS API**（合成语音） | AI 是产品的核心价值，不是装饰 |

### 2. 功能范围

**C 端 9 个页面**

| 页面 | 做什么 |
| --- | --- |
| 首页 | 首页 Banner 轮播、上传文章、选口吻、进历史 |
| 登录 | 微信授权登录，建立用户记录 |
| 生成中 | 解析与生成进度、剩余时间 |
| 确认页 | 逐条确认/修正可疑处（**人工确认点**） |
| 结果页 | 双音色播放、逐句高亮、点出处看原文、单句重做 |
| 历史记录 | 任务列表、续播、重试、删除 |
| 原文查看 | 出处回溯落地页，跳到对应段落并高亮 |
| 我的 | 用户信息、默认口吻偏好、清理缓存、退出 |
| 错误与降级 | 内容不适合转音频 / 语音合成不可用 |

**管理端 4 个页面**（加分项）

| 页面 | 做什么 |
| --- | --- |
| 管理首页 | 用户数、生成任务数、成功率、耗时趋势 |
| 用户管理 | 列表、搜索、封禁/解封、角色调整 |
| **Banner 管理** | 新增、编辑、排序、上下架、定时（老师点名要求） |
| 口吻模板管理 | 维护 6 种口吻的 Prompt 模板——**直接决定生成质量**，是本项目特有的管理项 |

**16 个组件**，覆盖上传、口吻选择、进度、可疑处确认、对话条目、播放器、逐句同步、
出处浮层、任务条目、空状态、管理端表格与统计卡，以及 uni-ui / ColorUI 的库组件。

**云数据库 10 张表**，其中老师点名的两张必须有：

- `users` —— 用户管理（openid、昵称、角色、状态）
- `banners` —— 首页轮播（图片、排序、上下架、起止时间）

其余为业务表：`tones`（口吻模板）、`articles`（文章）、`paragraphs`（段落）、
`scripts`（对话稿）、`dialogue_lines`（对话条目）、`audio_segments`（音频片段）、
`gen_logs`（生成日志，供管理端统计）、`feedbacks`（用户反馈）。

### 3. 三条硬约束（它们决定了架构，不是可选项）

1. **密钥不能放前端。** 大模型和 TTS 的 Key 若写在小程序代码里，解包即可拿到，等于公开泄露。
2. **小程序有域名白名单。** 请求域名必须 HTTPS 且已备案，直连第三方 API 往往过不了。
3. **主包上限 2MB。** 音频不能打进包，必须存云存储、按 URL 播放。

**结论：所有第三方调用必须经「云函数」中转。**

```
小程序端  →  云函数（持有密钥、组装请求）  →  大模型 API / TTS API
                    ↓
              云数据库 / 云存储
```

附带好处：以后换模型供应商，前端**一行都不用改**。

### 4. 要交的三样东西

| 提交物 | 要求 |
| --- | --- |
| **信息架构图** | 思维导图版（中心发散结构，不是流程图） |
| **录屏演示** | 手机或模拟器录屏 + 语音解说；必须讲到 5 点：目标用户、解决的问题、创新点（业务+技术）、功能演示（含插件来源/组件/模板）、源代码目录结构 |
| **源代码压缩包** | 前后端全部源码 + **云数据库导出**（导出后须给 openid 打码） |

### 5. 完成度硬指标

| 指标 | 门槛 | 本项目 |
| --- | --- | --- |
| 完整页面 | ≥ 6 | **13** |
| 不同组件 | ≥ 10 | **16** |
| 云数据库 | 含用户管理、banner | **10 张表**（两张已含） |
| 第三方后端 | 大模型 API 等 | 大模型 + TTS |
| 管理端 | 加分 | **做，4 页** |

另需**说明编程比例及插件来源**（哪些是 AI 辅助、用了哪些组件库及其版本与地址）。
若引入模板插件，**必须自己充分了解模板**——这一点在录屏时会被问到。

## 三、不做什么（划清边界，防止范围蔓延）

| 不做 | 原因 |
| --- | --- |
| 账号密码注册 | 只用微信授权，够用且省事 |
| 社交功能（评论、分享排行） | 与"听文章"这个核心无关 |
| 多语言 | 不在要求内 |
| 承诺小程序锁屏播放 | 小程序后台播放限制多，**别在录屏里吹做不到的能力**（见下方风险） |
| 长音频版权处理 | 用户上传自有资料，不涉及 |
| 自建服务器 | 用 uniCloud，不租机器、不配备案域名 |

- [ ] 一条完整链路能跑通：上传文章 → 生成对话稿 → 确认可疑处 → 合成音频 → 播放 → 点出处 → 单句重做
- [ ] 管理端能真实改到数据（改完 C 端可见）

**提交上：**
- [ ] 信息架构图 PNG（思维导图版）
- [ ] 录屏 + 语音解说（5 个必讲点全覆盖）
- [ ] 源代码压缩包（前后端 + 云数据导出，openid 已打码）

## 五、最容易踩的三个坑

| 坑 | 后果 | 对策 |
| --- | --- | --- |
| 云函数同步等大模型返回 | 生成一条对话稿可能超 20 秒，请求超时 | 拆成"提交任务 → 轮询结果"，别做同步长请求 |
| 音频打进小程序包 | 主包超 2MB，传不上去 | 音频一律走云存储 |
| ColorUI 不熟被问倒 | 要求明写"须充分了解模板" | 提前读其类名规则与设计变量，能当场讲 |
